Prompts para llevar un modelo a producción

Un asistente de código convierte un modelo entrenado en una API en un minuto, y casi siempre deja afuera lo que el curso enseñó: el esquema de entrada, la versión en cada respuesta, el registro de predicciones, el canario y la alerta de deriva. Este capítulo convierte el curso en plantillas de prompts para un modelo de aprendizaje automático y en una lista para revisar lo que el asistente entrega.

Antes de que existiera el servicio del capítulo 5, Andrés hizo un intento por su cuenta. El CRM quería consultar el modelo de mora cliente por cliente, cuando un agente abre la ficha. Andrés abrió su asistente de código y escribió: «Hazme una API con FastAPI que cargue modelo.pkl y devuelva la probabilidad de mora». En un minuto tenía un servicio de veinte líneas que respondía. Recibía una lista de ocho valores, la pasaba al modelo y devolvía la probabilidad.

Valeria lo probó con un cliente real y la respuesta tenía sentido. Después cambió el orden de dos números, como podría hacerlo un sistema que arma la lista con otra versión de la tabla. El servicio respondió igual de tranquilo, con una probabilidad absurda. Mandó un -5 en los días de atraso: otra probabilidad. Preguntó qué versión del modelo había respondido: el servicio no lo sabía. «Funciona», dijo, «pero si mañana se degrada, nos enteramos por Cobranzas».

Del cuaderno al servicio: lo que el asistente omite si no se pide

Imagínalo así

Si le pides a un electricista «pon un enchufe en la cocina», pone un enchufe. Si no le dices que ahí va el horno, no pone un circuito aparte, ni un interruptor diferencial, ni anota en el tablero qué enchufe es cuál. El enchufe funciona el primer día. El problema aparece el día que salta todo y nadie sabe por qué.

Un asistente de código optimiza lo que le pides: que el código corra. Aprendió de miles de tutoriales que muestran el camino feliz, y un servicio de modelo en un tutorial es exactamente el de veinte líneas: cargar el archivo, recibir números, devolver la predicción. Lo que el curso mostró en diez capítulos no aparece porque nada en el pedido lo exige y porque, en la primera prueba, ninguna de esas piezas cambia el resultado.

Lo que falta se puede ordenar por etapa del ciclo de vida, y cada etapa es un prompt de este capítulo:

  • Entrenar: semillas, versión de los datos, registro del experimento, validación de los datos antes de entrenar (capítulos 2 y 3).
  • Servir: un esquema de entrada (input schema, la lista de campos con su tipo y su rango) validado, la versión del modelo en cada respuesta, un tiempo límite (timeout) y un registro de cada predicción (capítulo 5).
  • Desplegar: modo sombra, canario y reversión (capítulo 6).
  • Monitorear: deriva de las entradas y de las predicciones, alertas con umbral y la señal que dispara el reentrenamiento (capítulos 7 y 8).
  • Variables: que el servicio calcule las variables igual que el entrenamiento (capítulo 4).

El prompt corto era este:

Hazme una API con FastAPI que cargue modelo.pkl y devuelva la probabilidad de mora.

Las secciones que siguen lo reemplazan por un archivo de instrucciones y un prompt por etapa. No son frases mágicas: son especificaciones (specifications), escritas para que un asistente las cumpla y para que una persona pueda comprobar que se cumplieron. Cómo escribir prompts profesionales para una aplicación con un modelo de lenguaje, con su evaluación y su seguridad, está en Aplicaciones con IA; aquí el modelo es uno propio, y lo que importa es la reproducibilidad, el registro, el monitoreo y el reentrenamiento.

# Modelo de mora: instrucciones para asistentes de código

## Estructura
- datos/: solo lectura. Los datos se versionan con DVC; nunca se editan a mano.
- entrenamiento/: el pipeline (validar -> entrenar -> evaluar -> registrar).
- servicio/: la API de predicción. No importa nada de entrenamiento/ salvo
  variables/, que es compartido.
- variables/: única definición de cada variable. El entrenamiento y el servicio
  la usan igual.

## Registro de modelos
- Seguimiento y registro con MLflow (variable MLFLOW_TRACKING_URI).
- El modelo se llama "mora-30d". El servicio carga siempre models:/mora-30d@campeon,
  nunca un archivo suelto ni un número de versión escrito en el código.
- Mover el alias campeon lo hace una persona, nunca un script del asistente.

## Esquema
- servicio/esquema.py es la fuente del contrato: nombres, tipos y rangos.
  Un cambio de esquema es una versión mayor del servicio.

## Comandos
- Pruebas: python -m pytest -q
- Pipeline completo con datos de muestra: python -m entrenamiento.pipeline --muestra
- Validación de datos: python -m entrenamiento.validar datos/actual.parquet

## Reglas
- Toda aleatoriedad usa la semilla de config.yml.
- Ningún dato personal en registros ni en artefactos (el cliente va como id).
- No se agregan dependencias sin fijar su versión en requirements.txt.

## Terminado significa
- Pruebas en verde, pipeline de muestra corriendo de punta a punta y el modelo
  nuevo registrado con sus métricas, sin moverle el alias.

Tres detalles hacen que funcione. Las reglas se pueden verificar: «carga models:/mora-30d@campeon» se revisa con una búsqueda; «usa buenas prácticas» no. Los comandos están completos, así que el asistente los corre en lugar de suponer. Y hay una frontera explícita entre lo que hace el asistente y lo que hace una persona: registrar un modelo sí, moverle el alias no.

Prompt para el pipeline de entrenamiento

Imagínalo así

Una receta de panadería industrial no dice «harina a gusto». Dice qué harina, de qué lote, cuántos gramos, a qué temperatura y cuánto tiempo, y cada tanda queda anotada. Si un día el pan sale distinto, se compara la planilla de ese día con la de ayer.

El capítulo 3 convirtió el cuaderno en un pipeline. El prompt pide exactamente eso, con números y con pruebas:

Contexto: proyecto descrito en el archivo de instrucciones. Python 3.12,
scikit-learn y MLflow con las versiones de requirements.txt.

Construye entrenamiento/pipeline.py con cinco pasos en funciones separadas:
1. cargar(version_datos): lee la versión de datos indicada (etiqueta de DVC)
   y registra su huella (hash) como parámetro del experimento.
2. validar(df): rechaza la tabla y detiene el pipeline si falta una columna,
   si un tipo no coincide, si más del 2 % de una columna es nulo, si un valor
   cae fuera del rango de servicio/esquema.py o si aparece gestion_cobranza,
   que se registra después del vencimiento. El reporte dice qué falló.
3. entrenar(df, semilla): toda aleatoriedad (partición, modelo) usa la semilla
   de config.yml. La partición es por fecha: entrena con los meses anteriores
   y prueba con el último, nunca al azar.
4. evaluar(modelo, prueba): AUC, precisión y exhaustividad con el umbral de
   config.yml, y la misma métrica por tramo de antigüedad.
5. registrar(...): un experimento de MLflow con parámetros, métricas, versión
   de datos, commit de Git y la firma de entrada. Solo si el AUC de prueba
   es al menos 0,75 registra el modelo como "mora-30d" con la etiqueta de su
   versión de datos. No mueve el alias.

Pruebas que debes escribir:
- dos corridas con la misma semilla y los mismos datos -> mismas métricas
- una tabla sin la columna dias_atraso_prom_6m -> validar falla con un
  mensaje que la nombra
- una tabla con fechas mezcladas -> la prueba nunca contiene meses anteriores
  a los de entrenamiento

Los requisitos responden a fallas concretas del curso. La huella de los datos y el commit permiten el linaje del capítulo 2. La partición por fecha y la variable prohibida atacan la fuga de datos (data leakage) del capítulo 1: gestion_cobranza le hizo prometer al cuaderno un AUC de 0,86 que en producción no existía, y una partición al azar puede hacer algo parecido, porque el modelo se prueba con meses que «ya vio». La métrica por tramo detecta un modelo que mejora el promedio y empeora para los clientes nuevos. Y la prohibición de mover el alias deja la decisión de producción en manos de una persona, como en el capítulo 8.

Prompt para servir el modelo

Imagínalo así

En la ventanilla de un banco, el cajero no acepta un cheque con la fecha en blanco o con la cifra en letras distinta de la cifra en números: lo devuelve y dice por qué. Y cada operación que acepta queda anotada con su número, su hora y quién la atendió.

Esta es la pieza que falló en la historia del principio. El capítulo 5 explicó cómo servir; el prompt fija el contrato:

Construye servicio/app.py con FastAPI: POST /v1/predecir.

Contrato:
- Entrada: {"cliente_id": str, "antiguedad_meses": int 0..600,
  "precio_plan": float 1..500, "metodo_pago": "debito" | "tarjeta" |
  "efectivo" | "transferencia" | "billetera", "dias_atraso_prom_6m": float
  0..365, "facturas_tarde_12m": int 0..12, "reclamos_90d": int 0..50,
  "bajo_plan_3m": 0 | 1, "pago_parcial_3m": 0 | 1}. Campos por nombre,
  nunca una lista posicional. Campos extra o faltantes, tipos o rangos inválidos -> 422 con
  {"error": {"code", "message", "campo"}}.
- Salida 200: {"prob_mora": float, "umbral": 0.30, "en_lista": bool,
  "version_modelo": str, "prediccion_id": str}.

Requisitos:
1. Al arrancar carga models:/mora-30d@campeon. Si no puede, el proceso no
   queda sirviendo: /salud responde 503 y el despliegue lo detecta.
2. Las variables se calculan con variables/, el mismo código del entrenamiento.
3. Tiempo límite de 300 ms por predicción; si se supera, 503 con el sobre de
   error. Nunca un 500 con la traza de la excepción.
4. Registra cada predicción: prediccion_id, hora, versión del modelo, entradas
   (sin datos personales), probabilidad y latencia. Ese registro alimenta el
   monitoreo y se une después con la mora real.
5. GET /salud y GET /version (nombre, versión del modelo, commit del servicio).

Pruebas: una por fila del contrato (campo extra, campo faltante, tipo, cada
rango), el modelo que no carga -> /salud 503, y una predicción cuya respuesta
trae la misma versión que quedó en el registro.

Mira dónde se concentra el valor. «Campos por nombre, nunca una lista posicional» elimina de raíz el error de las columnas cambiadas. Los rangos convierten un -5 en un 422 con el nombre del campo, en lugar de una probabilidad inventada. La lista cerrada de metodo_pago obliga a decidir de antemano qué pasa con un método nuevo, como la billetera del capítulo 1: aquí se acepta porque el negocio la ofrece, aunque el modelo no la haya visto al entrenar, y el monitoreo cuenta cuánto crece. La versión en cada respuesta y en el registro es el linaje del capítulo 2 llevado a cada predicción. Y el registro de predicciones es la materia prima del monitoreo: sin él no hay deriva que medir.

Prompt para el despliegue: shadow, canario y reversión

Imagínalo así

Un piloto nuevo vuela primero en el simulador, después de copiloto con un capitán al lado y recién entonces al mando, en rutas cortas. Y siempre hay un procedimiento escrito para devolver el control si algo sale mal.

El capítulo 6 enseñó a cambiar el modelo sin apostarlo todo. El prompt pide la infraestructura que lo hace posible y, sobre todo, las condiciones escritas para avanzar y para volver:

Agrega al servicio el despliegue progresivo de una versión retadora.

1. Modo sombra: si la variable RETADOR está definida, el servicio carga
   también models:/mora-30d@retador, calcula su predicción para cada petición
   y la registra con su versión, pero responde solo con la del campeón.
   La sombra no puede sumar más de 50 ms a la latencia: si tarda, se omite.
2. Canario: la variable PORCENTAJE_CANARIO (0 a 100) decide qué parte de las
   peticiones responde el retador. El reparto es por cliente_id (hash), para
   que un mismo cliente vea siempre la misma versión.
3. Reversión: poner PORCENTAJE_CANARIO=0 vuelve todo al campeón sin desplegar
   ni reiniciar. Documenta el comando exacto en el README.
4. Condiciones automáticas de reversión, evaluadas cada 15 minutos:
   latencia p95 del retador > 1,5 veces la del campeón, tasa de errores > 1 %
   o diferencia en el porcentaje de clientes en la lista > 5 puntos. Si se cumple una,
   el canario vuelve a 0 y se avisa al canal del equipo.
Pruebas: el mismo cliente_id cae siempre del mismo lado; con 0 % nadie recibe
al retador; una sombra lenta no cambia la latencia del campeón.

El reparto por cliente evita que un agente vea al mismo cliente marcado en riesgo un día y no al siguiente, solo porque cayó en otra versión. Las condiciones de reversión escritas antes de empezar son la diferencia entre un canario y una esperanza: sin números, el equipo discute en medio del incidente si «está peor o es ruido». La integración continua que construye y prueba la imagen del servicio es la de DevOps; aquí se pide lo propio del modelo.

Prompt para el monitoreo: deriva, alertas y reentrenamiento

Imagínalo así

Un médico no espera a que el paciente se desmaye para tomarle la presión. La toma en cada control, la compara con la de la vez anterior y tiene un número a partir del cual pide más exámenes. Y no llama a urgencias por cada décima de diferencia.

El capítulo 7 midió la deriva y el 8 decidió cuándo reentrenar. El prompt los convierte en un trabajo programado con umbrales:

Construye monitoreo/deriva.py, que corre cada día a las 6:00 sobre el
registro de predicciones de las últimas 24 horas.

1. Referencia: la distribución de cada variable en los datos de entrenamiento
   del modelo con el alias campeon (guárdala al registrar el modelo, con
   10 tramos por cuantiles).
2. Deriva de datos: PSI por variable (para metodo_pago, sobre la proporción
   de cada categoría). Umbrales: < 0,1 estable; 0,1 a 0,2
   vigilar; > 0,2 alerta. Con menos de 500 predicciones no calcula: lo dice.
3. Deriva de predicciones: PSI de la probabilidad y porcentaje de clientes
   en la lista del día frente a la media de las 4 semanas anteriores.
4. Desempeño: cuando llega la mora real (45 días después de emitida la
   factura), une por prediccion_id y calcula el AUC por semana.
5. Alertas: una alerta solo si el umbral se supera dos días seguidos, con la
   variable, el valor, el gráfico y el enlace al tablero. Agrupa en un solo
   mensaje las variables que saltan el mismo día.
6. Reentrenamiento: si el AUC semanal cae bajo 0,75 o hay alerta de deriva
   7 días seguidos, abre una tarea de reentrenamiento con el reporte. No
   reentrena ni despliega solo.
Pruebas: una variable desplazada medio desvío -> PSI > 0,2 dos días -> una
alerta; datos iguales a la referencia -> ninguna; 300 predicciones -> no calcula.

Fíjate en dos decisiones. La regla de «dos días seguidos» y el agrupamiento son la diferencia entre alertas que sirven y alertas que cansan, el tema del capítulo 7: un equipo que recibe diez mensajes por la mañana deja de leerlos. Y el último requisito no deja que el sistema se reentrene y se despliegue solo: abre una tarea con el reporte, y la decisión pasa por el campeón contra retador del capítulo 8. Para un modelo que decide a quién llama Cobranzas, la aprobación humana es parte del gobierno, como explica IA responsable.

Revisar lo generado: la lista de verificación antes de producción

Un prompt completo sube mucho la probabilidad de recibir lo que pediste, pero no la lleva a uno. El asistente puede cumplir nueve requisitos y saltarse el décimo con la misma seguridad, o escribir una prueba que no prueba nada. Por eso lo generado se revisa con una lista, y cada punto tiene una forma de comprobarlo que no depende de leer todo el código.

EtapaQué se revisaCómo se comprueba
EntrenarSemilla, versión de datos, partición por fecha, registro sin aliasCorrer el pipeline dos veces y comparar las métricas; buscar la huella de datos en el experimento
VariablesUna sola definición para entrenamiento y servicioBuscar que el servicio importe variables/ y no reescriba fórmulas
ServirCampos por nombre, rangos, versión en cada respuesta, tiempo límiteEnviar peticiones mal formadas y mirar el 422; leer el registro de una predicción
ArranqueEl servicio no sirve sin modeloApuntar a un alias inexistente y ver /salud en 503
DesplegarSombra que no suma latencia, canario por cliente, reversión con una variablePoner el canario en 0 y comprobar que nadie recibe al retador
MonitorearPSI con umbral, dos días seguidos, alertas agrupadas, reentrenamiento que no se despliega soloCorrer el monitoreo con datos desplazados y con datos iguales a la referencia

Dos señales de alarma en lo generado: pruebas que cargan el modelo real desde el registro de producción (lentas, frágiles y peligrosas) y pruebas que solo verifican que la función «devuelve algo». Una prueba útil fija una entrada y un resultado exacto. Cuando algo falla, lo eficiente no es corregirlo a mano: se le devuelve al asistente la salida de la prueba y se le pide que corrija el código sin tocar las pruebas.

Primero, el modelo y su referencia. Guarda este programa como preparar.py y córrelo con python preparar.py: entrena con el mes 0, como el cuaderno honesto, y deja modelo.joblib y referencia.json con la distribución de cada variable en el entrenamiento.

"""Entrena el modelo con el mes 0 y guarda la referencia para medir la deriva."""
import json
import joblib
import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

NUMERICAS = ["antiguedad_meses", "precio_plan", "dias_atraso_prom_6m", "facturas_tarde_12m",
             "reclamos_90d", "bajo_plan_3m", "pago_parcial_3m"]
m0 = pd.read_csv("datos/clientes-m00.csv")
prep = ColumnTransformer([("num", StandardScaler(), NUMERICAS),
                          ("cat", OneHotEncoder(handle_unknown="ignore"), ["metodo_pago"])])
modelo = make_pipeline(prep, LogisticRegression(max_iter=1000)).fit(m0, m0.mora_30d)
joblib.dump({"modelo": modelo, "version": "4", "columnas": NUMERICAS + ["metodo_pago"]},
            "modelo.joblib")

referencia = {}
for c in ["metodo_pago", "precio_plan"]:   # pocas opciones: proporción de cada valor
    referencia[c] = {"categorias": {str(k): v for k, v in m0[c].value_counts(normalize=True).items()}}
for c in [c for c in NUMERICAS if c != "precio_plan"]:   # 10 tramos por cuantiles
    cortes = sorted(set(np.quantile(m0[c], np.linspace(0, 1, 11)[1:-1]).tolist()))
    tramos = np.searchsorted(cortes, m0[c], side="right")
    referencia[c] = {"cortes": cortes,
                     "proporciones": (np.bincount(tramos, minlength=len(cortes) + 1) / len(m0)).tolist()}
json.dump(referencia, open("referencia.json", "w"), indent=2)
print("modelo.joblib y referencia.json listos")

"""Prueba el contrato del servicio: peticiones mal formadas y un mes de deriva."""
import csv, json, urllib.error, urllib.request

BASE = "http://127.0.0.1:8000"

def pedir(ruta, cuerpo=None):
    datos = json.dumps(cuerpo).encode() if cuerpo is not None else None
    req = urllib.request.Request(BASE + ruta, data=datos, headers={"Content-Type": "application/json"})
    try:
        with urllib.request.urlopen(req, timeout=10) as r:
            return r.status, json.load(r)
    except urllib.error.HTTPError as e:
        try:
            return e.code, json.loads(e.read() or b"{}")
        except ValueError:
            return e.code, {}
    except OSError:
        return 0, {}

BUENA = {"cliente_id": "20417", "antiguedad_meses": 30, "precio_plan": 30.0,
         "metodo_pago": "efectivo", "dias_atraso_prom_6m": 4.5, "facturas_tarde_12m": 1,
         "reclamos_90d": 0, "bajo_plan_3m": 0, "pago_parcial_3m": 0}
SIN_ATRASO = {k: v for k, v in BUENA.items() if k != "dias_atraso_prom_6m"}
CASOS = [
    ("normal", BUENA, 200),
    ("lista posicional", {"cliente_id": "1", "valores": [30, 30.0, "efectivo", 4.5, 1, 0, 0, 0]}, 422),
    ("campo con otro nombre", {**SIN_ATRASO, "dias_atraso": 4.5}, 422),
    ("valor imposible", {**BUENA, "dias_atraso_prom_6m": -5}, 422),
    ("tipo incorrecto", {**BUENA, "antiguedad_meses": "treinta"}, 422),
    ("campo de más", {**BUENA, "nombre": "Carmen Rojas"}, 422),
]
malos = 0
for nombre, cuerpo, espera in CASOS:
    codigo, resp = pedir("/v1/predecir", cuerpo)
    fallas = [] if codigo == espera else [f"código {codigo}, se esperaba {espera}"]
    if espera == 200 and not resp.get("version_modelo"):
        fallas.append("la respuesta no trae la versión del modelo")
    if espera == 422 and "error" not in resp and "detail" not in resp:
        fallas.append("el error no dice qué campo falló")
    malos += bool(fallas)

La idea clave

Un servicio de modelo no está listo porque responde. Está listo cuando cada entrada se valida contra un esquema, cada predicción lleva su versión y queda registrada, el cambio de modelo pasa por sombra y canario con condiciones de reversión escritas, y una alerta con umbral avisa antes de que el negocio note la degradación. El asistente construye lo que se le pide: se le pide por escrito, con un archivo de instrucciones, un prompt por etapa y pruebas que cualquier versión del código debe pasar.

Pruébate

¿Por qué el prompt de servir exige «campos por nombre, nunca una lista posicional»?

Porque con una lista, un cliente que manda los valores en otro orden recibe una predicción absurda sin ningún error. Con campos por nombre, un nombre que no coincide da 422.

¿Qué permite que la respuesta lleve la versión del modelo y que esa versión quede en el registro de predicciones?

Reconstruir el linaje de cada predicción, comparar versiones durante un canario y unir después la predicción con la mora real para medir el desempeño de cada versión.

¿Por qué el prompt de entrenamiento pide partir por fecha y no al azar?

Para evitar la fuga de datos: con una partición al azar el modelo se prueba con meses que ya vio, y su métrica promete más de lo que dará en producción.

En el prompt de monitoreo, ¿para qué sirve exigir que el umbral se supere dos días seguidos y agrupar las alertas?

Para que las alertas sirvan y no cansen: un día raro no dispara nada y un mismo problema llega en un solo mensaje.

¿Por qué el monitoreo abre una tarea de reentrenamiento en lugar de reentrenar y desplegar solo?

Porque el modelo nuevo debe ganarle al campeón y pasar una aprobación humana, como parte del gobierno del modelo.
