Versionar datos, código y modelos

Andrés no pudo repetir su propio modelo porque nadie había guardado con qué datos, qué código y qué parámetros se hizo. Este capítulo versiona las tres cosas que cambian con Git, DVC y MLflow, guarda el modelo de mora en un registro con alias y aprobaciones, y le pone una tarjeta que dice para qué sirve y para qué no.

Las tres cosas que cambian: datos, código y modelo

La primera pregunta de Valeria a Andrés fue simple: «¿con qué datos sacaste el 0,86?». Andrés buscó en su laptop y encontró clientes_sep.csv, clientes_sep_final.csv y clientes_sep_final2.csv. Ninguno daba 0,86. El cuaderno había cambiado tantas veces que el código de aquel día tampoco existía. El modelo estaba en un archivo modelo_final.pkl, sin fecha ni historia. El número era real, pero ya no se podía comprobar.

Imagínalo así

Un laboratorio clínico no entrega solo un número. El informe dice de qué muestra salió, cuándo se tomó, qué reactivo se usó, con qué lote y en qué equipo calibrado. Si el médico duda, el laboratorio puede repetir el examen en las mismas condiciones. Un resultado que no se puede rastrear hasta su muestra no sirve para decidir, por bueno que parezca.

Un modelo de aprendizaje automático es el resultado de tres cosas que cambian por separado, y hay que guardar la versión de cada una:

  • Los datos. La tabla de clientes de septiembre no es la de octubre, y una misma tabla puede corregirse después. Cambian sin que nadie toque el código.
  • El código. El script que limpia, calcula variables y entrena. Cambia cuando alguien corrige un error o prueba una idea.
  • El modelo. El artefacto que sale del entrenamiento: los coeficientes, el preprocesamiento y todo lo necesario para predecir. Un artefacto (artifact) es cualquier archivo que produce un proceso y que hay que guardar.

Hay una cuarta pieza que se olvida seguido: los parámetros y el entorno. Los parámetros (hyperparameters) son los valores que eliges antes de entrenar, como la fuerza de la regularización C o la semilla; el entorno, las versiones de Python y de las librerías. Con los mismos datos y el mismo código, otra versión de scikit-learn puede dar decimales distintos.

Cuando las cuatro piezas tienen versión y están conectadas, existe el linaje (lineage) del modelo: la cadena que va de cada predicción a la versión del modelo que la hizo, de esa versión a la corrida que la entrenó y de la corrida a sus datos, su código y sus parámetros. Con el linaje completo puedes responder la pregunta que tarde o temprano hace alguien: «¿por qué este cliente estaba en la lista?».

El código con Git (a fondo en DevOps)

El código se versiona con Git, y casi todos los equipos ya lo hacen. Cada commit (confirmación) guarda una foto de todos los archivos y recibe un identificador único, un hash como 7eb9bf3, que se obtiene con git rev-parse --short HEAD. Ese identificador es el que se anota junto a cada entrenamiento: dice exactamente qué código produjo el modelo. Las ramas, los pull requests, las etiquetas de versión y la integración continua están a fondo en DevOps.

En un proyecto de ML, lo importante es lo que no va en Git:

  • Datos grandes. Git guarda cada versión de cada archivo completa, y la historia crece sin freno. GitHub, por ejemplo, rechaza archivos de más de 100 MB.
  • Modelos binarios. Un .pkl o un .onnx cambia entero con cada entrenamiento y no se puede comparar línea a línea.
  • Secretos. Claves de bases de datos y de APIs van en un gestor de secretos, nunca en el repositorio.

Lo que sí va: el código, la configuración (un config.yaml con el umbral, las variables y las rutas), el archivo de dependencias con versiones exactas y unos archivos chicos que apuntan a los datos y a los modelos. Esos punteros son el truco de la sección siguiente.

Versionar datos: DVC, lakeFS y tablas con historia

Versionar datos tiene un problema que el código no tiene: el tamaño. La solución común es no guardar los datos en Git, sino guardar en Git una huella de los datos y los datos mismos en otro lugar.

Imagínalo así

En el guardarropa de un teatro no te devuelven el abrigo por su descripción: te dan una ficha con un número. La ficha cabe en el bolsillo; el abrigo queda colgado atrás. Mientras tengas la ficha, recuperas exactamente tu abrigo, aunque haya mil iguales. DVC hace eso con los datos: Git guarda la ficha y el almacén guarda el abrigo.

DVC (Data Version Control, control de versiones de datos) es una herramienta de código abierto que trabaja junto a Git. Al ejecutar dvc add datos/clientes-m00.csv, DVC calcula un hash (resumen) del archivo con el algoritmo MD5: una cadena de 32 caracteres que cambia por completo si cambia un solo byte. Copia el archivo a una caché local, escribe un archivo pequeño clientes-m00.csv.dvc con el hash y el tamaño, y agrega el CSV al .gitignore para que Git no lo suba. Git versiona el .dvc; los datos van con dvc push a un remoto (remote): un bucket de S3, Google Cloud Storage o Azure, un servidor por SSH o, para practicar, una carpeta local. Quien clone el repositorio ejecuta dvc pull y recibe exactamente esos bytes.

DVC no es la única forma. Hay tres familias, y conviene elegir según dónde viven los datos:

HerramientaCómo versionaCuándo encaja
DVCHash de cada archivo, puntero en Git, datos en un remotoArchivos (CSV, Parquet, imágenes) que el equipo de ML prepara y usa para entrenar
lakeFSRamas y commits sobre un almacén de objetos completo, sin copiar los datosUn lago de datos (data lake) compartido por varios equipos, donde se quiere probar cambios en una rama aislada
Tablas con historia (Delta Lake, Apache Iceberg)Cada escritura crea una instantánea; se consulta el estado de una fecha o versión anteriorDatos que ya viven en tablas grandes de un lakehouse; basta anotar la versión de la tabla

En las tablas con historia, la consulta del pasado se llama viaje en el tiempo (time travel). En Delta Lake se escribe, por ejemplo, SELECT * FROM clientes VERSION AS OF 12. Para el modelo de mora, anotar «tabla clientes, versión 12» cumple el mismo papel que el hash de DVC. Cómo se construyen esos lagos y tablas está en Ingeniería de datos.

Seguimiento de experimentos: parámetros, métricas y artefactos con MLflow

Valeria y Andrés probaron, en una semana, regresiones logísticas con distintos C, árboles, bosques y boosting. Al tercer día ya nadie recordaba cuál había dado qué. El seguimiento de experimentos (experiment tracking) es anotar cada entrenamiento de forma automática, con todo lo necesario para compararlo y repetirlo.

Imagínalo así

Un buen cocinero que prueba variantes de una salsa lleva una libreta: qué cambió, cuánto de cada cosa, cómo quedó, quién la probó. Sin la libreta, la mejor salsa de la semana se pierde el lunes. El seguimiento de experimentos es esa libreta, pero la escribe el propio código mientras entrena.

MLflow es la herramienta de código abierto más usada para esto, y el curso la usa en sus prácticas. Sus conceptos:

  • Experimento (experiment): un grupo de corridas sobre el mismo problema, por ejemplo mora-30d.
  • Corrida (run): un entrenamiento, con un identificador único como eb874da3.
  • Parámetros (params): los valores de entrada, como C = 1.0, el hash de los datos o el commit del código.
  • Métricas (metrics): los resultados, como el AUC y el recall (sensibilidad) con umbral 0,30: de cada 100 clientes que caen en mora, cuántos estaban en la lista.
  • Artefactos (artifacts): archivos que produce la corrida, empezando por el modelo, guardado con su firma (signature), el esquema de las columnas que espera y lo que devuelve.

MLflow separa dónde guarda cada cosa: los parámetros y las métricas van a una base de datos de seguimiento (en las prácticas, un archivo SQLite llamado mlflow.db) y los artefactos, a un almacén de artefactos (artifact store), que en la práctica es una carpeta y en producción suele ser un bucket. Para scikit-learn existe además mlflow.sklearn.autolog(), que anota casi todo sin escribir una línea; aquí se anota a mano para ver qué se guarda. Weights & Biases, Neptune y los servicios gestionados de las grandes nubes (Vertex AI, SageMaker, Azure Machine Learning) son ejemplos del mercado que cumplen el mismo papel.

En la terminal

Anota dos corridas del modelo de mora en MLflow

Vas a entrenar el modelo de mora dos veces con distintos C, con el hash de los datos y el commit del código anotados en cada corrida, y a compararlas en la interfaz de MLflow. Sigue en la carpeta mora-30d, con el entorno activado y los datos de la práctica anterior. MLflow pesa unos cientos de MB.

"""Entrena el modelo de mora y lo anota todo en MLflow."""
import argparse
import subprocess
from pathlib import Path

import mlflow
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import recall_score, roc_auc_score
from sklearn.model_selection import train_test_split
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

NUMERICAS = ["antiguedad_meses", "precio_plan", "dias_atraso_prom_6m", "facturas_tarde_12m",
             "reclamos_90d", "bajo_plan_3m", "pago_parcial_3m"]
CATEGORICAS = ["metodo_pago"]

p = argparse.ArgumentParser()
p.add_argument("--C", type=float, default=1.0)
p.add_argument("--datos", default="datos/clientes-m00.csv")
a = p.parse_args()

# El linaje: con qué datos (hash de DVC) y con qué código (commit de Git)
hash_datos = Path(a.datos + ".dvc").read_text().split("md5: ")[1].split()[0]
commit = subprocess.run(["git", "rev-parse", "--short", "HEAD"], capture_output=True, text=True).stdout.strip()

df = pd.read_csv(a.datos)
X, y = df[NUMERICAS + CATEGORICAS], df.mora_30d
ent_X, pru_X, ent_y, pru_y = train_test_split(X, y, test_size=0.3, random_state=42, stratify=y)
prep = ColumnTransformer([("num", StandardScaler(), NUMERICAS),
                          ("cat", OneHotEncoder(handle_unknown="ignore"), CATEGORICAS)])
modelo = make_pipeline(prep, LogisticRegression(C=a.C, max_iter=1000))

mlflow.set_tracking_uri("sqlite:///mlflow.db")
mlflow.set_experiment("mora-30d")
with mlflow.start_run():
    modelo.fit(ent_X, ent_y)
    prob = modelo.predict_proba(pru_X)[:, 1]
    mlflow.log_params({"C": a.C, "variables": len(NUMERICAS + CATEGORICAS), "semilla_split": 42,
                       "datos": a.datos, "datos_md5": hash_datos, "git_commit": commit})
    mlflow.log_metrics({"auc": roc_auc_score(pru_y, prob),
                        "recall_umbral_030": recall_score(pru_y, prob >= 0.30)})
    info = mlflow.sklearn.log_model(modelo, name="modelo", input_example=pru_X.head(3),
                                    registered_model_name="mora-30d")
    print(f"AUC {roc_auc_score(pru_y, prob):.3f} | version registrada {info.registered_model_version}")

git commit -m "Script de entrenamiento con MLflow"

mlflow ui --backend-store-uri sqlite:///mlflow.db --port 5000
  1. Abre http://127.0.0.1:5000 en el navegador. En el experimento mora-30d, selecciona las dos corridas y pulsa «Compare».
  2. Abre una corrida y busca, en los parámetros, datos_md5 y git_commit. En la pestaña de artefactos, abre el archivo MLmodel.
  3. Detén el servidor con Ctrl+C en la terminal cuando termines.

Qué observar: las dos corridas aparecen en una tabla con sus parámetros y métricas lado a lado. El AUC es casi idéntico (0,789 y 0,790): bajar C cien veces casi no cambia nada con 14.000 clientes de entrenamiento, y el registro lo muestra antes de que alguien lo presente como una mejora. Cada corrida guarda el hash de los datos y el commit, así que el linaje queda escrito por el propio código. Cada entrenamiento creó además una versión de mora-30d en la pestaña «Models», sin alias todavía. No subas mlflow.db ni la carpeta mlruns a Git: son el almacén de esta práctica.

El registro de modelos: versiones, etapas y aprobaciones

Un registro de modelos (model registry) es el catálogo de los modelos que pueden llegar a producción. Cada vez que se registra un modelo, el registro crea una versión numerada que nunca cambia: la versión 1 de mora-30d será siempre el mismo artefacto, con el enlace a la corrida que lo produjo. Así el linaje sigue vivo aunque pasen años.

Imagínalo así

El registro de modelos funciona como el registro de medicamentos aprobados de un país. Cada fórmula tiene su número y su ficha, y nadie la cambia: una fórmula nueva es un registro nuevo. Las farmacias no deciden qué vender mirando los laboratorios; venden lo que el registro autoriza. Y cuando un medicamento se retira, el registro guarda su historia.

Durante años, MLflow organizó las versiones en etapas (stages): Staging (en prueba), Production (en producción) y Archived (archivada). Desde la versión 2.9, MLflow las desaconseja y propone alias (aliases) y etiquetas (tags): un alias es un nombre que apunta a una sola versión y se puede mover; una etiqueta es un dato libre, como quién aprobó. Otras herramientas siguen hablando de etapas, pero la idea es la misma: el servicio no pide «el archivo nuevo», pide «el modelo que hoy está en producción», y el registro dice cuál es.

El curso usa tres alias para el modelo de mora:

  • campeon: la versión que usa producción. El servicio carga siempre models:/mora-30d@campeon.
  • candidata: una versión que pasó las reglas automáticas y espera aprobación.
  • retador: una versión que compite con el campeón en producción, en sombra o en canario (capítulos 06 y 08).

Para que una versión reciba el alias candidata, tiene que pasar cinco reglas, y para pasar a campeon, una persona tiene que aprobarla:

  1. No usa variables prohibidas, como gestion_cobranza.
  2. Su métrica se midió con datos que no vio en el entrenamiento.
  3. La brecha entre el AUC de entrenamiento y el de validación es de 0,05 o menos: si es mayor, el modelo memorizó en lugar de aprender, lo que se llama sobreajuste (overfitting).
  4. Su AUC es de al menos 0,75 si no hay campeón, o supera al campeón por 0,01 o más si lo hay.
  5. Tiene su tarjeta de modelo completa (la última sección).

La aprobación final es de la gerente de Cobranzas, dueña del caso, junto con Valeria. El registro guarda quién aprobó y cuándo, en una etiqueta de la versión: es la pista de auditoría.

Pon un alias y carga el campeón sin saber qué versión es

Vas a darle el alias campeon a la versión 1, cargar el modelo por su alias desde otro script y, después, mover el alias a la versión 2 sin tocar el código del servicio. Sigue en mora-30d, con las dos versiones de la práctica anterior.

"""Carga el modelo con alias «campeon» y predice el mes 3."""
import mlflow
import pandas as pd

mlflow.set_tracking_uri("sqlite:///mlflow.db")
cliente = mlflow.MlflowClient()
version = cliente.get_model_version_by_alias("mora-30d", "campeon")
corrida = cliente.get_run(version.run_id)
print(f"Campeon: mora-30d version {version.version}, corrida {version.run_id[:8]}")
print(f"Entrenado con {corrida.data.params['datos']} (md5 {corrida.data.params['datos_md5'][:8]}) "
      f"y el commit {corrida.data.params['git_commit']}")

modelo = mlflow.sklearn.load_model("models:/mora-30d@campeon")
mes3 = pd.read_csv("datos/clientes-m03.csv")
prob = modelo.predict_proba(mes3)[:, 1]
print(f"Mes 3: {(prob >= 0.30).sum()} de {len(mes3)} clientes entran a la lista")

Qué observar: el script nunca nombra una versión ni un archivo, y aun así imprime qué versión cargó, con qué datos y con qué commit se entrenó: el linaje completo a partir de un alias. Al mover el alias a la versión 2, el mismo script carga otro modelo sin cambiar una línea; el número de clientes en la lista del mes 3 casi no cambia, porque las dos versiones son casi iguales. Mover un alias es la forma más simple de desplegar y de volver atrás, y por eso conviene que solo lo haga quien aprueba.

Un caso real

«¿Por qué a mí?». En varios países, quien usa un modelo para decisiones de crédito debe poder explicarle a una persona por qué se le negó o se le cobró más, y en la Unión Europea la Ley de IA clasifica la evaluación de solvencia de personas como un uso de alto riesgo, con obligaciones de registros y documentación técnica. Equipos de riesgo que operan bajo esas reglas cuentan la misma lección: la pregunta no llega el día del entrenamiento, sino meses después, por un reclamo o una auditoría, y la única forma de contestarla es haber guardado el linaje desde el principio. Reconstruir con qué datos y qué versión se decidió algo, después, cuesta semanas o es imposible.

Tarjetas de modelo (la transparencia a fondo está en IA responsable)

El registro dice qué versión hay y de dónde viene. No dice para qué sirve, para qué no, ni dónde falla. Eso va en una tarjeta de modelo (model card), un documento corto que propusieron Margaret Mitchell y otros en 2019 y que hoy acompaña, por ejemplo, a casi todos los modelos públicos de Hugging Face.

Imagínalo así

El prospecto de un medicamento dice para qué está indicado, la dosis, las contraindicaciones y los efectos adversos. Nadie lo lee por gusto, pero el día que hace falta, ahí está. Un modelo sin tarjeta es un frasco sin prospecto: puede funcionar bien, y aun así nadie sabe cuándo no tomarlo.

La tarjeta de la versión 1 del modelo de mora, en Markdown y guardada como artefacto de la corrida:

# Tarjeta de modelo: mora-30d, versión 1
Dueña: gerente de Cobranzas · Responsable técnica: Valeria · Aprobado: 28 de enero
Uso previsto: ordenar a los clientes por riesgo de mora a 30 días el día de emisión de
  la factura, para la lista de gestión preventiva (recordatorio y acuerdo de pago).
Fuera de alcance: decidir cortes, cambiar precios o negar el servicio a un cliente.
Datos: clientes-m00.csv (md5 44d5c0a1), 20.000 clientes sintéticos, mora del 7,5 %.
Variables: 8 (historial de pagos, plan, método de pago, reclamos). Prohibida: gestion_cobranza.
Métricas (30 % de validación): AUC 0,789; recall con umbral 0,30: 0,24.
Limitaciones: no conoce métodos de pago nuevos; la etiqueta se conoce 45 días después.
Desempeño por grupos: pendiente de medir por método de pago y por antigüedad.
Revisión: mensual, con el monitoreo del capítulo 07.

Fíjate en dos líneas. «Fuera de alcance» protege al modelo de que lo usen para lo que no se hizo: una lista para llamar no es un sistema para cortar. Y «desempeño por grupos» queda pendiente a propósito: medir si el modelo se equivoca más con unos clientes que con otros, y qué hacer si pasa, es tema de IA responsable.

En la práctica

La regla de Valeria. Después de esta semana, el equipo escribió una sola regla en el archivo de instrucciones del proyecto: «ningún modelo llega a producción si no se puede rastrear». En la práctica significa que el pipeline se niega a registrar una corrida sin hash de datos ni commit, que el servicio solo carga modelos por alias y que cada fila de la lista guarda la versión que la calculó. La primera vez que la regla molestó fue cuando Andrés quiso probar «rapidito» un cambio desde su cuaderno; la primera vez que sirvió fue tres meses después, cuando un cliente reclamó por una llamada y la respuesta tardó diez minutos en lugar de una semana.

La idea clave

Linaje completo: de cada predicción a los datos y el código que la hicieron posible. Los datos se versionan con una huella (DVC, lakeFS o tablas con historia), el código con Git, cada entrenamiento se anota con sus parámetros y métricas, y el modelo vive en un registro con versiones que no cambian, alias que se mueven con aprobación y una tarjeta que dice para qué sirve.

Pruébate

¿Qué guarda Git cuando versionas un CSV con DVC?

Solo el archivo .dvc, con el hash MD5, el tamaño y el nombre. Los datos quedan en la caché local y en el remoto de DVC.

Dos corridas dan AUC 0,789 y 0,790. ¿Por qué la segunda no puede ser campeona si la primera ya lo es?

Porque la regla exige superar al campeón por 0,01 o más; una diferencia de 0,001 puede ser ruido de la partición y no justifica cambiar el modelo en producción.

¿Por qué el servicio carga models:/mora-30d@campeon y no una versión con número?

Para que desplegar o volver atrás sea mover el alias en el registro, con aprobación, sin cambiar el código del servicio.

Una corrida tiene AUC 1,000 en entrenamiento y 0,570 en validación. ¿Qué regla no pasa y qué le pasó al modelo?

La de la brecha: es de 0,43, muy por encima de 0,05. El modelo memorizó los datos de entrenamiento (sobreajuste) y no generaliza.

La lista guarda la probabilidad de cada cliente, pero no la versión del modelo. ¿Qué pregunta ya no se puede contestar?

Qué modelo hizo cada predicción; y con eso se pierden también sus datos, su código y sus parámetros, porque solo se alcanzan a través de la versión.
